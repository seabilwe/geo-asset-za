# Performance report

Generated by `administration/performance/benchmark.py`. Re-run it to reproduce these figures on your own machine.

## Test conditions

- PostgreSQL 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1), PostGIS 3.4.2, shared_buffers 128MB, work_mem 4MB
- Parallel query switched off, so every timing is one process and runs are comparable
- Benchmark table `bench.asset_points`: 2,000,000 synthetic points across the City of Tshwane, 197 MB on disk, inserted in random order
- Each figure is the median of 7 warm runs (cache already loaded), measured with `EXPLAIN (ANALYZE, BUFFERS)`
- GiST index built in 4.3 s (79 MB); `CLUSTER` on that index took 10.2 s

## Spatial queries in three states

1. **No index**: every query scans the whole table.
2. **GiST index**: `CREATE INDEX ... USING gist (geom)`.
3. **GiST index, table clustered**: `CLUSTER ... USING` the GiST index rewrites the table so that points close on the ground are stored on the same disk pages.

## Register query: composite index on inspections

Latest condition of every streetlight in the register (DISTINCT ON over 80,000 inspections): 55.1 ms without `inspections_asset_date_idx`, 30.8 ms with it (2× faster). At 80,000 inspections the gain is modest; it grows with the history.

## What the results show

- **Selective queries gain the most.** A 1 km box, a 250 m radius or the 10 nearest assets touch a tiny share of the table. With the GiST index PostgreSQL reads only the matching index pages instead of testing every row.
- **The plan's example box is a poor test of an index.** It covers most of the built-up area, so about two thirds of all points match. Here the index made the query *slower* than a full scan: the planner chose an index scan, and because the rows were stored in random order it had to jump between table pages for every match (see pages touched). After `CLUSTER`, matching rows sit together on disk and the same plan reads far fewer pages.
- **How a query is written decides whether the index can be used.** Casting the column to geography (`geom::geography`) hides it from the geometry index, so the planner falls back to a full scan even when an index exists. Adding a bounding-box condition on the raw column (`geom && ST_Expand(...)`) lets the index find candidates first; the exact distance in metres is then checked on those few rows only.
- **Nearest-neighbour search** with `ORDER BY geom <-> point LIMIT 10` walks the GiST index in distance order and stops after ten rows; without the index every distance has to be computed and sorted.
- **CLUSTER is a one-off.** PostgreSQL does not keep the order as rows are added, so it is repeated in a maintenance window when the table has changed a lot. It locks the table while it runs.
